# 0004. Контракт cream/v1 в 1.2: фаза сама, `cream check`, `cream.json`, configure по отметке, `every_boot`, `scope: build`

- **Status:** Accepted
- **Date:** 2026-10-21
- **Deciders:** владелец cream
- **Tags:** format, cli, state, exit-codes

## Контекст и проблема
bisquite 3.0.0 становится дистрибутивом cream: везёт `.deb` cream и снимок каталога по пину, ставит cream в гостя
скрытым шагом сразу после `FROM`, а расширения ставятся обычным `RUN_COMMAND cream install …` (спека
[bisquite с встроенным cream](../specs/2026-10-21-bisquite-bundled-cream.md), §0, §10). Для этого cream 1.2.0 должен
сам понимать, что он внутри `virt-customize`, ставить из источника в фазе build, проверять строки VMFILE на хосте
без root и сети и сообщать состав образа файлом. Владелец заодно решил, что configure выполняется **один раз до
успеха**, а не на каждой загрузке, и что код `20` хука configure — «пропущено», а не ошибка.

Всё это — изменения контракта `cream/v1` (ADR 0001): формат манифеста (два новых поля), CLI (новая команда,
новое умолчание фазы), пути на машине (`/etc/image-labels.d/cream.json`, `/var/lib/cream/configured/`), смысл
кода хука. Мажор менять нельзя — bisquite 2.x, каталог 5.x и Stvor живут на `cream/v1`.

Отдельная проблема — **как старый cream встречает манифест с новым полем.** 1.1.x разбирает манифест строго:
`every_boot` для него — «неизвестное поле», `scope: build` — «допустимо config или install». Автор расширения из
такого ответа не поймёт, что нужен cream новее.

## Рассмотренные варианты
- **A — минор `cream/v1` (1.2.0): всё аддитивно, новые поля манифеста требуют `cream: ">=1.2.0"`.** Как стадии
  configure в 1.1.0. Старый cream отказывает по `cream:` (68 `platform.cream_version`) раньше строгого разбора.
- **B — `cream/v2`.** Честно для смены умолчаний (фаза, configure один раз), но рвёт весь каталог и bisquite 2.x ради
  изменений, которые укладываются в «только добавляем».
- **C — новые поля без требования `cream:`, старый cream их игнорирует.** Ломает строгий разбор (ADR 0001) и молча
  меняет смысл: `every_boot: false` на 1.2.0 — «один раз», а на 1.1.x configure шёл бы на каждой загрузке;
  `scope: build` превратился бы в хранимый ключ — секрет сборки лёг бы в образ.

## Решение
Вариант A. cream 1.2.0 — минор контракта `cream/v1`:
1. **Фаза определяется сама** (спека §10.1): `--phase` → `CREAM_PHASE` родителя → автоопределение по PID 1
   (`systemd` и `/run/systemd/system` — `live`; иначе — `build`; `/proc` не читается — 64 `phase.undetermined`).
2. **`install`/`upgrade`/`remove` в фазе build из источника** (§10.2); `--from-dir`/`--record` и `resolve` остаются
   устаревшими до cream 2.0.
3. **`cream check`** (§10.3) — офлайн-проверка шагов на хосте; `resolve` — обёртка над ней.
4. **`/etc/image-labels.d/cream.json`** (§8.2, §10.4) — состав установленного; путь и форма — контракт.
5. **configure по отметке выполнения** `/var/lib/cream/configured/<ext>.json` (§10.7): на загрузке хук не
   запускается, если отметка совпала с реестром (`version`, `ext_digest`, `params_digest`, `secrets_rev`,
   `machine_id`); `cream configure --force`, `--again`.
6. **Код `20` хука configure** — `skipped`: не ошибка, отметка не пишется, повтор на следующей загрузке (§10.8).
7. **Поле `hooks.configure.every_boot`** (bool, по умолчанию `false`) — configure на каждой загрузке, мимо отметки.
8. **Значение `scope: build`** у ключа `config.keys` — третье в перечислении `config|install|build`: значение живёт
   только в окружении хуков текущей операции `install`/`upgrade` и нигде на машине не хранится (§10.9).
9. **Таблица «поле → версия» (`checkSince`)**: стадии `early|cloud-user|graphical` — 1.1.0, `every_boot` (любое
   значение) и `scope: build` — 1.2.0. Манифест с полем новее своего `cream:` — 65 `manifest.invalid` с
   `details.field` и `details.since`. `checkCream` стоит до строгого разбора, поэтому cream 1.1.x отвечает на такой
   манифест 68 `platform.cream_version`, а не «неизвестное поле»; это закреплено контрактной фикстурой
   `testdata/contract/` и проверкой `make contract-old` релизным 1.1.4 в CI.

## Обоснование
ADR 0001 разрешает в минорах только добавлять, и каждое решение выше — добавление: новое поле, новое значение
перечисления, новая команда, новый файл. Смена умолчаний (фаза, configure один раз) не ломает работающих
потребителей: `live` по-прежнему выбирается на машине с systemd, а bisquite 2.x передаёт `--phase build` явно;
хуки configure по контракту идемпотентны, а те, кому мало одного прогона, получают `every_boot: true` по аудиту
каталога (§10.7, признаки А1–А6). Требование `cream: ">=1.2.0"` превращает непонятный отказ старого cream в
понятный и не даёт `scope: build` тихо стать хранимым ключом.

## Последствия
- **Положительные:** bisquite ставит расширения обычным `cream install` в госте; загрузка с десятком расширений
  не гоняет десяток хуков; секрет сборки не попадает в домен; автор манифеста получает точную подсказку о версии.
- **Отрицательные:** у configure два режима (по отметке и `every_boot`) — аудит каталога обязателен до выпуска
  минора cream-extensions; в CI cream появляется сетевой шаг (скачивание релиза 1.1.4, сверка sha256).
- **Действия:** реализация по плану [bisquite-bundled-cream](../plans/2026-10-21-bisquite-bundled-cream.md)
  (Task 2, 4, 5, 7, 8, 10, 11, 13, 15); справочники манифеста, CLI, путей и кодов выхода — в Task 17; минор
  каталога с `every_boot` и `cream: ">=1.2.0"` — после выпуска 1.2.0.
- **Временный запрет снят (Task 10):** до реализации области build движок отказывал `install`/`upgrade`/`set`
  расширения с ключом `scope: build` — 64 `scope.build_unsupported`. Task 10 снял запрет вместе с реализацией:
  - значения ключей `scope: build` (`K=V`, `K=- <` stdin, `--params-file`) выделяются из параметров до домена и
    попадают только в окружение хука `install`/`upgrade` этой операции (умолчания — под заданными значениями); в
    `config`/`secrets` домена, `params_digest` (в том числе слоя `cream resolve` и пути `--from-dir`),
    `history.jsonl` и `cream.json` их нет; секретные (`secret: file`) вымарываются в выводе хука, в argv секрет
    по-прежнему запрещён (64 `secret.in_argv`);
  - `cream set`/`get` такого ключа — 64 `config.scope_build`; `cream show`, `config export --shell` и окружение
    `configure`/`apply`/действий их не содержат;
  - обязательный ключ (`empty: false` без `default`, манифест такой ключ принимает только для `scope: build`) без
    значения — 64 `config.build_required` на операции install (до дерева); на upgrade не требуется;
  - повтор `install` той же версии без смены параметров установки хук не запускает — значения сборки не
    применяются, предупреждение `install.build_unused` (переприменить — `--reinstall`).
