## 0. Вводные владельца (не пересматриваются)
- Целевое железо: Raspberry Pi 4/5, другие arm64, amd64, виртуальные машины. **Роутеры и слабое железо (MIPS,
  32-битный ARM, < 1 ГБ ОЗУ, флеш в десятки МБ) не поддерживаем.**
- Машина на OpenWrt заводится в Teleport и Stvor **одной командой из портала**, как робот на Debian/Ubuntu.
- Только **OpenWrt 25.12+** (`apk`), 24.10/`opkg` не поддерживаем (В1). Минимум машины — **1 ГБ ОЗУ и 1 ГБ свободно
  на корне** (В6; 1 ГБ ОЗУ подтверждён PoC).
- Приёмка — ВМ на PVE-ноде `root@192.168.202.206` (VMID 990001–990010, ВМ после себя удалять); RPi 4/5 — у владельца.
- Пользователи стенда для проверок — CRUD разрешён владельцем на dev-стенде, только с префиксом `owrt-*`.

## 1. Цели и не-цели
**Цели**
1. Узел Teleport на OpenWrt: регистрация `token`/`bound_keypair`, метки, приложения, вход `tsh ssh` через SSO — как у
   робота на Debian.
2. stvor-agent на OpenWrt держит метки узла равными порталу и шлёт телеметрию (как на Debian после 4.1.0).
3. Портал выдаёт команду установки для OpenWrt; зеркало стенда раздаёт всё нужное.
4. Регистрация **переживает перезагрузку**; после ручного `sysupgrade` с сохранением конфигурации узел возвращается
   сам, тем же `host_uuid`, без действий на портале (Р4).

**Не-цели**
- Роутеры, MIPS, armv7, машины с ОЗУ < 1 ГБ или < 1 ГБ свободного места на корне.
- OpenWrt 24.10 и старше, `opkg`, пакеты `.ipk`/`.apk` для cream и stvor-agent (В1, В5).
- Обновление прошивки средствами cream или Stvor (ОС не обновляем; решение владельца 2026-10-18).
- Настройка сети/firewall OpenWrt: узел ходит к прокси исходящим обратным туннелем.
- BPF-запись сессий, PAM, `create_host_user` на OpenWrt; рабочие станции на OpenWrt; строки «Загрузок» для OpenWrt.
- Изменения cream (слой готов в 1.3.0) и `openwrt-builder` (нужные образы уже выпущены, §2.2).

## 2. Факты
### 2.1 OpenWrt
| Факт | Значение и следствие |
|---|---|
| Версии | стабильная — **25.12.6**; 24.10 «outdated». Поддерживаем 25.12+ (В1) |
| libc | musl; `gcompat` и glibc в фидах нет |
| init | procd: `/etc/init.d/<имя>`, `START=NN`, `rc.d`; `respawn`; журнал — `logread`, `journalctl` нет |
| `/var` | ссылка на `/tmp` (tmpfs): всё под `/var` (кроме `/var/run` по смыслу) пропадает при перезагрузке |
| `sysupgrade` | переписывает корень; сохраняет `/etc/config`, `/etc/sysupgrade.conf`, `/lib/upgrade/keep.d/*` (архивом в ОЗУ) |
| `os-release` | `ID=openwrt`, `VERSION_ID=25.12.x` (`SNAPSHOT` не поддерживается) |
| В базовом образе | busybox (`ash`, `sha256sum`, `tar -z`), `uclient-fetch` как `wget`; `bash`/`curl` — не всегда (в образах `openwrt-builder` есть: `bash`, `curl`, `ca-bundle`) |
| Пользователи | только `root` с shell (`/bin/ash`); системных учёток создаёт `/lib/functions.sh` `user_add`/`group_add_next` (так делают пакеты OpenWrt) |
| `machine-id` | `/etc/machine-id` нет |
| `uclient-fetch` и POST | `--post-data=''` шлёт POST с пустым телом (исходник `openwrt/uclient`); проверка строки на чистой ВМ — приёмка |

| Что | Результат |

| patchelf | `--set-interpreter /opt/teleport/lib/ld-linux-… --set-rpath /opt/teleport/lib` на 386-МБ бинаре — секунды; `/proc/self/exe` = `/opt/teleport/bin/teleport` |

| Не проверено | **`tsh ssh root@узел`** (классификатор отклонил создание пользователя), arm64, нагрузка SSH-сессий, `bound_keypair` |

## 3. Teleport: вариант A — решение
**Вариант A (glibc-рантайм рядом + patchelf) — основной и подтверждённый** (В3). Вариант B (сборка форка под musl)
остаётся запасным **только** если `tsh ssh` (первая задача плана) упрётся в glibc на чужой системе (utmp, NSS, PTY);
переход на B — стоп и решение владельца (+1–2 недели).

Решения по PoC (обязательны для `openwrt/teleport-openwrt` и проверяются тестами расширения):
1. **procd без перехвата вывода:** init-скрипт **не** ставит `procd_set_param stdout/stderr` — иначе procd
   выставляет `LD_PRELOAD=/lib/libsetlbf.so` (musl) и в glibc-процесс загружаются обе libc. Журнал узла —
   **файл** `log.output: /opt/teleport/log/teleport.log` (каталог 0700, файл 0600), **не syslog**: в syslog любой
   локальный процесс пишет любой тег с любым pid (`logger -t 'teleport[1234]'`), а по журналу `join` решает об
   отказе кластера. Размер держит экземпляр procd `logcap`: раз в 10 мин (и перед стартом) журнал больше 1 МиБ
   копируется в `teleport.log.1` и усекается на месте (copy-truncate; Teleport открывает журнал с `O_APPEND`,
   `lib/utils/log`), журнал — на `/opt`, не в tmpfs. Отказ кластера засчитывается только по этому файлу и только
   пока в `data_dir` нет identity. Тесты расширения: в init-скрипте нет `stdout`/`stderr`; строки `logger` с тегом
   `teleport[<pid>]` решений не меняют; предел журнала держится под писателем с `O_APPEND`.
2. **`ssh_service.pam.enabled: false`** и **`ssh_service.enhanced_recording.enabled: false`** — явно (PAM и BPF нет).
3. **Раскладка:** `/opt/teleport/bin/{teleport,fdpass-teleport}` (+ ссылка `/usr/bin/teleport` для удобства —
   `/proc/self/exe` раскрывает её в настоящий путь), `/opt/teleport/lib/` (рантайм), `data_dir: /opt/teleport/data`,
   `TMPDIR=/opt/teleport/tmp` (`procd_set_param env`), конфиг — `/etc/teleport.yaml`.
4. `os_logins` — только `root`; учётки не создаются; `utmp` нет, `wtmp` на tmpfs — предупреждения в журнале
   при сессиях допустимы.
5. Набор `openwrt-<arch>` — **без `tsh`** (Р2): `tar.gz` с каталогом `teleport/{teleport,fdpass-teleport,lib/,SHA256SUMS}`
   (бинари после `patchelf` на `/opt/teleport/lib`), имя — `teleport-v<v>-openwrt-<arch>-bin.tar.gz`; скрипт Stvor
   скачивает его плоско, как остальные файлы бутстрапа, и передаёт расширению через `TELEPORT_TARBALL=` (отдельная
   раскладка `<mirror>/binaries/teleport/<v>/…` не нужна); ставится всегда по `TELEPORT_SHA256`.

## 4. Архитектура по слоям
### 4.1 cream — без изменений
Всё нужное есть в 1.3.0 (§2.2). Расширения этой спеки объявляют `platform.family: openwrt`, `cream: ">=1.3.0"`.
Если по ходу всплывёт дефект cream — отдельный PR в cream по обычному циклу, не правка контракта.

### 4.2 cream-extensions: `teleport-openwrt` и `stvor-agent-openwrt` в общем снимке (Р11)
- Имя уникально во всём каталоге, а `teleport` и `stvor-agent` заняты `extensions/debian`. Поэтому OpenWrt-расширения
  называются **`teleport-openwrt`** и **`stvor-agent-openwrt`** и лежат в существующем корне `extensions/openwrt/`
  (`roots: [extensions/debian, extensions/openwrt]` не меняется) — **один** манифест, **один** снимок
  `cream-extensions-<v>.tar.gz`, один пин `CREAM_EXTENSIONS_SHA256` у Stvor. `stvor-agent-openwrt` —
  `depends: [teleport-openwrt]`. Бандл bisquite получает оба расширения тем же снимком.
- Имя `teleport` зашито ровно в трёх местах вне каталога: stvor-agent (`internal/teleport/cream.go` — `managed-status`,
  `set-managed`, `actions --json`) и скрипт Stvor. stvor-agent выбирает имя по семейству из `/etc/os-release` (то же
  определение, что для `initsys`, §4.3); ветка `openwrt` скрипта Stvor ставит `teleport-openwrt`/`stvor-agent-openwrt`.
- **Общее ядро `teleport` (Р3, уточнён Р11):** init-независимая часть `teleport.sh` (рендер `teleport.yaml`, join,
  метки, `apps.d`, `bound_keypair`, managed-метки) — **одна копия в git**, `lib/teleport-core.sh`. Потребители
  (`debian/teleport`, `openwrt/teleport-openwrt`) объявляют `files/teleport-core.sh`; файл кладёт
  `tools/catalog-snapshot.sh` в снимок и `tools/stage-catalog.sh` в staged-дерево (на нём работают `cream validate`,
  H-тесты, живые тесты и path-источник). `tools/check.sh` сверяет: копий в git нет, у потребителей есть строка
  `files`, копии в снимке байтово равны `lib/`; `check-version-bump.sh`: правка ядра поднимает версии **всех**
  потребителей. Подсказки ядра называют расширение из переменной слоя (`TELEPORT_EXT`). Ядро запускает бинарь как
  `env -u LD_PRELOAD "$TELEPORT_BIN"` — страховка к §3 п. 1. Тесты ядра — одни (`lib/tests/`), тесты слоёв — в своих
  расширениях. Контракт cream/v1 не меняется.
- **Тонкие слои** (`teleport.sh` семейства подключает `teleport-core.sh`):
  | Точка | debian | openwrt |
  |---|---|---|
  | init | `teleport.service`, `teleport-join.{service,timer}`, `teleport-{token,apps}.{path,service}` | `/etc/init.d/teleport` (`USE_PROCD=1`, `START=95`, `respawn`, **без stdout/stderr**); повтор join — procd-экземпляр `join` (цикл раз в минуту, пока есть `join-pending`; кончается сам); экземпляр `logcap`; вместо `.path` — прямой вызов `reload-apps` |
  | перезапуск | `systemctl restart --no-block` | `/etc/init.d/teleport restart &` |
  | журнал join | `journalctl -u teleport` | файл `/opt/teleport/log/teleport.log` (0700/0600, `logcap` 1 МиБ) с отсечкой по времени; отказ — только без identity |
  | архитектура | `dpkg --print-architecture` | `uname -m` → `amd64`/`arm64` |
  | данные, «зарегистрирован» | `/var/lib/teleport`, `host_uuid` | `/opt/teleport/data`, `host_uuid` |
  | временные файлы | `/tmp` | `TMPDIR=/opt/teleport/tmp` |
  | тарбол | `linux-<arch>` с `tsh` | `openwrt-<arch>` без `tsh`, с `lib/` |
  | `teleport.yaml` | как сейчас | `log.output: /opt/teleport/log/teleport.log`, `pam`/`enhanced_recording` выключены |
- **`debian/teleport`** переходит на ядро без изменения поведения (минор, `4.2.0`); регресс — его тесты без правок
  ожиданий + живой прогон (`make test-live`) + `robots-gate` Stvor на Debian перед подъёмом пина.
- **`openwrt/teleport-openwrt`**: те же ключи `config.keys`, что у debian (контракт со скриптом Stvor), `TELEPORT_TARBALL`
  указывает на набор `openwrt-<arch>`; `platform.commands: [bash, curl, tar, sha256sum]`; `files`:
  `/etc/init.d/teleport`, `/lib/upgrade/keep.d/teleport` (§4.7); хук `install` пишет маркер `/opt/teleport/.cream-owned`
  и возвращает `0700` каталогу состояния (после `sysupgrade` tar восстанавливает его `0755`).
- **`keep.d` расширений** (Р4, 2026-10-23): `teleport-openwrt` — `/opt/teleport/data`, маркер, домен
  `/etc/cream/teleport-openwrt/` (прокси, имя токена, env, метки, `apps.d`; секрета нет) и флаг
  `/opt/cream/var/ext/teleport-openwrt/agent-enabled`; `stvor-agent-openwrt` — `/lib/upgrade/keep.d/stvor-agent`
  (состав — §4.3).
- **`openwrt/stvor-agent-openwrt`** (`depends: [teleport-openwrt]`): `stvor-agent_<v>_linux_<arch>.tar.gz` по `files/pin.env` (те же ключи
  `STVOR_AGENT_VERSION/SHA256/MIRROR`, вместо `STVOR_AGENT_DEB` — `STVOR_AGENT_TARBALL`); бинарь в `/usr/bin`;
  init-скрипты `/etc/init.d/stvor-agent` и `/etc/init.d/stvor-agent-telemetry` (procd, `respawn`; Go-бинарь
  статический — `LD_PRELOAD` ему безвреден, `stdout/stderr 1` допустимы); пользователь телеметрии — `user_add` из
  `/lib/functions.sh` в хуке `install` (Р8); `platform.commands: [tar, sha256sum]`.
- Хуки — bash (`bash` в `platform.commands`; скрипт Stvor ставит его сам, §4.5).

### 4.3 stvor-agent на OpenWrt (Р8)
- **Сборка:** без изменений — `CGO_ENABLED=0`, статический; новый ассет релиза `stvor-agent_<v>_linux_{amd64,arm64}.tar.gz`
  (бинарь, man, LICENSE, NOTICE) в том же `SHA256SUMS`, воспроизводимый (`repro-check`).
- **Init как интерфейс:** `internal/systemd` → `internal/initsys` с `systemd` и `procd`; выбор — по семейству из
  `/etc/os-release` (как cream, РО1), не флагом. procd: `/etc/init.d/<svc> enable|restart|stop|disable`.
- **Имя расширения по семейству** (Р11): `teleport-openwrt` на `openwrt`, `teleport` иначе — в трёх вызовах `cream`
  (`internal/teleport/cream.go`).
- **Пути по семейству:** на `openwrt` — состояние `/opt/stvor-agent/state.json`, телеметрия `/opt/stvor-agent/telemetry/`
  (вместо `/var/lib/…`, tmpfs); токены `/etc/stvor-agent/token` и `/etc/stvor-agent-telemetry/token` — как есть
  (`/etc` переживает reboot); `/run/stvor-agent.lock` — как есть.
- **Токены и состояние в `keep.d`** (Р4, решение владельца 2026-10-23; прежний запрет снят): `stvor-agent-openwrt`
  кладёт в `/lib/upgrade/keep.d/stvor-agent` `/opt/stvor-agent/{machine-id,state.json,telemetry-token.src}`,
  `/etc/stvor-agent/token`, `/etc/stvor-agent-telemetry/token` и домен `/etc/cream/stvor-agent-openwrt/`.
  **Почему:** без них агент после `sysupgrade` не может говорить с порталом, а выдать новые можно только новым
  секретом регистрации — и тогда Teleport 18.10 даёт новый `host_uuid` (§4.7). Архив `sysupgrade` и так содержит ключ
  узла Teleport и `/etc/shadow`, токены агента уровень секретности не повышают. Права после распаковки чинит
  существующий механизм расширения (configure `every_boot`, пересоздание буфера без рекурсивного `chown`).
  **Риски:** архив `sysupgrade` (и выгрузка `sysupgrade -b` / резервная копия LuCI) — **секрет уровня root**: кто его
  получил, тот выдаёт себя за робота. Восстанавливать его **только на ту же машину**: на другой получится клон
  (тот же узел и токены; детектор клонов Stvor ловит его по `machine-id` агента). При удалении робота — отзыв токенов
  агента и `tctl lock` на server-id узла. Описывается в руководстве (README расширения, runbook 10 Stvor).
- **Без `machine-id`:** на `openwrt` агент при первом старте создаёт `/opt/stvor-agent/machine-id` (128 бит случайных) и
  берёт хеш от него; образ bisquite его не содержит (служба в фазе build не стартует), поэтому клоны различаются.
- **Телеметрия:** сборщики терпят отсутствие `/proc/pressure/*` (ядро OpenWrt без `CONFIG_PSI`) и `/home`; служба
  телеметрии — под пользователем `stvor-telemetry` (`procd_set_param user`).
- **Песочницы нет** (ни `ProtectSystem`, ни `NoNewPrivileges`) — фиксируется в `SECURITY.md` агента.
- Ветвится от `main` **после** слияния телеметрии; выходит в релизе после 4.1.0 (номер — по release-please, решение
  с сессией Stvor).

### 4.4 Teleport-набор `openwrt-<arch>` на стенде Stvor (Р7)
- Собирает **стенд Stvor** (`make up` → `fetch-teleport`), не машина и не CI чужого репозитория: новый
  `scripts/build-teleport-openwrt.sh` в контейнере `debian:12` (образ по digest) из уже сверенного тарбола
  `linux-<arch>` и `.deb` `libc6` + `libgcc-s1` Debian 12 **по пинам sha256** (`snapshot.debian.org`, файл пинов в
  репозитории Stvor, например `teleport/openwrt-glibc.env`); `dpkg-deb -x` (без эмуляции — arm64 собирается на amd64),
  `patchelf` из Debian 12; архив детерминирован (`--sort=name`, `--mtime`, `--owner=0`, `gzip -n`).
- Результат сверяется с пином экземпляра **`TELEPORT_OPENWRT_SHA256_<ARCH>`** (`.env.example`, отдельные строки);
  сбой сборки — WARN в `fetch-teleport` (`make up` не обрывается), но **заданный пин без собранного набора или с
  чужой суммой — FAIL** в env-preflight и `smoke` (Р13); `check-teleport-pin.sh` сверяет формат пина. `patchelf` —
  тоже `.deb` Debian 12 по пину из `openwrt-glibc.env`, без `apt`. Две сборки одного входа — одни байты (тест).
- Подъём Teleport (runbook Stvor): шаг «пересобрать набор `openwrt-<arch>`, обновить `TELEPORT_OPENWRT_SHA256_*`».
- **arm64** — тот же путь: официальный тарбол CE `linux-arm64` (как сейчас) + `libc6:arm64`, интерпретатор
  `ld-linux-aarch64.so.1`. Выпуск arm64-набора на prod разрешён (В7 закрыт).
- Раскладка на зеркале: `teleport/dist/teleport-v<ver>-openwrt-<arch>-bin.tar.gz` + `<файл>.sha256`, раздаётся по
  `/dist/teleport/` как остальное; скрипт скачивает его плоско и передаёт `TELEPORT_TARBALL=` (§3 п. 5).

### 4.5 Stvor: скрипт установки и портал
- **Один универсальный скрипт** (В2), ветка `openwrt`: ОС — `ID=openwrt`, `VERSION_ID >= 25.12`; архитектура —
  `uname -m`; проверки **до любых изменений**: root, ОЗУ ≥ 1 ГБ, свободно ≥ 1 ГБ на `/opt` и на `/tmp` для самого
  скрипта, набор для архитектуры в пинах (Р5), «Teleport не от cream» (`/etc/init.d/teleport` или
  `/opt/teleport/data/host_uuid` при пустом `cream list` — только с маркером `/opt/teleport/.cream-owned`, иначе
  отказ); рабочий каталог — `mktemp -d /opt/stvor-install.XXXXXX`; зависимости — `apk add bash curl ca-bundle`
  (есть — пропуск; офлайн — требуются заранее); cream — `tar.gz` в `/usr/bin` + `cream system init` (как
  [guides/openwrt.md](../guides/openwrt.md)), если стоит не ровно версия пина; источник — общий снимок каталога
  (как у Debian); дальше `cream install … teleport-openwrt` (с `TELEPORT_TARBALL` набора `openwrt-<arch>`),
  `cream run teleport-openwrt join` (секрет на stdin), `cream install stvor-agent-openwrt`; после успеха — служба
  `stvor-restore` с рецептом без секретов и `keep.d/stvor` (§4.7, Р4).
- **Набор бутстрапа по семейству** (`downloads.py`, `Bootstrap.arches`): OpenWrt-робот для `<arch>` доступен при
  тарболе cream `<arch>` (`CREAM_TARBALL_SHA256_<ARCH>`), общем снимке каталога (`CREAM_EXTENSIONS_SHA256`), наборе `TELEPORT_OPENWRT_SHA256_<ARCH>` и тарболе stvor-agent
  (`STVOR_AGENT_TARBALL_SHA256_<ARCH>`); версии — общие `CREAM_VERSION`, `CREAM_EXTENSIONS_VERSION`,
  `STVOR_AGENT_VERSION`. Пины — **отдельными строками** `.env.example`, поля — в конце тела `RuntimeSettings`
  (`settings.py`), переменные — своими строками в конце `x-runtime-env` (`compose.yaml`); env-preflight: пин без пары —
  отказ, как сейчас. `robot-pin-bump.sh` поднимает группу **целиком из одного `SHA256SUMS`** (cream: `.deb` + tar.gz;
  stvor-agent: `.deb` + tar.gz) и отказывает, если ассета группы нет (Р13).
- **POST** (Р1): `POST` к install-эндпоинту равноценен `GET` с `X-Stvor-Install: 1` (погашение кода, аудит);
  `HEAD`/`GET` без заголовка код не расходуют. Реализация — **отдельная функция в конце `robot_api.py`** (рядом
  идёт `POST /robot-api/v1/telemetry-token` сессии Stvor).
- **Портал** — две строки на `/robots/new` (`install_code.render_command` + `render_command_openwrt`, поле
  `InstallCodeOut.command_openwrt`): Debian/Ubuntu — без изменений; OpenWrt —
  `[ -s /etc/ssl/certs/ca-certificates.crt ] || {…отказ: apk add ca-bundle…} && uclient-fetch -qO- --post-data=''
  --ca-certificate=/etc/ssl/certs/ca-certificates.crt 'https://…/install/<код>' | sh` (busybox-`wget` сертификат не
  проверяет; все загрузки скрипта на OpenWrt — тоже `uclient-fetch` с проверкой CA). Строка OpenWrt показывается, только если на экземпляре
  есть хотя бы одна архитектура набора OpenWrt.
- **compose/Traefik — две узкие правки** (Р12): в роутере `robot-install` только `rule` (`` … && (Method(`GET`) ||
  Method(`POST`)) ``) и отдельный middleware `buffering` с `maxRequestBodyBytes` ≈ 1 КБ; роутер `robot-api`, приоритеты
  и роутеры сессии Stvor (`…-robot-telemetry-token`, `…-ingest`) не трогаются. Проверка — через Traefik (`smoke`/гейт):
  `POST` доходит до backend, большое тело — 413, `POST` на прочие `/robot-api/v1/*` в `robot-install` не попадает.

### 4.6 bisquite и openwrt-builder
- `openwrt-builder` — **не нужен** (образы 25.12.6 всех таргетов, `bash`/`curl`, рост корня — уже в v0.3.1).
- bisquite: пример **OpenWrt-робота** — образ на базе `openwrt-builder` v0.3.1 с предпосылками (без Teleport внутри:
  регистрация — командой портала после деплоя) и профиль деплоя `1 ГБ ОЗУ / диск 4 ГБ`; используется в приёмке.
  Расширения `teleport-openwrt`/`stvor-agent-openwrt` попадают в бандл bisquite с общим снимком (Р11); встраивать
  Teleport в образ — вне плана.

### 4.7 `sysupgrade` (В4, Р4; пересмотрено 2026-10-23)
- `sysupgrade` с сохранением конфигурации хранит идентичность (`/opt/teleport/data`, маркер, флаг `agent-enabled`),
  домены `/etc/cream/{teleport,stvor-agent}-openwrt`, токены и состояние агента и службу `stvor-restore` с рецептом
  без секретов. На первой загрузке служба после сети ставит apk-зависимости, cream и оба расширения по пинам и
  запускает узел без `join` — узел возвращается с тем же `host_uuid` без действий на портале. «Новый секрет» нужен
  только при потерянной идентичности (`sysupgrade -n`, новый диск); тогда узел получает новый `host_uuid`, а Stvor
  удаляет старый узел.
- **Почему так:** архив `sysupgrade` — это `/lib/upgrade/keep.d/*` и изменённые conffiles пакетов; пропадают
  `/usr/bin/cream`, `/opt/cream` (реестр), `/etc/init.d/*` и `rc.d` расширений, `/opt/teleport/{bin,lib}`, apk `bash`/
  `curl`/`ca-bundle`. `every_boot` cream не сработает (cream пропал), `uci-defaults` не годится (S10 — до сети,
  удаляется после первого успеха). Teleport сохранённую идентичность принимает: при прочитанном состоянии `join` не
  делается, перерегистрация — без токена. А `join` без живой Instance-идентичности в Teleport 18.10 **выдаёт новый
  host ID** — поэтому прежний путь «Новый секрет → та же команда» давал дубль узла.
- **Служба `stvor-restore`** (кладёт скрипт установки Stvor, только OpenWrt-ветка, после успешной установки):
  `/etc/stvor/restore.sh` — рецепт **без кода и секрета** (зеркало портала и пины sha256: tar.gz cream, снимок
  каталога, набор Teleport, tar.gz stvor-agent); `/etc/init.d/stvor-restore` (procd, `START=99`, повтор раз в минуту
  до успеха); `/lib/upgrade/keep.d/stvor` — `/etc/stvor/`, `/etc/init.d/stvor-restore`, `/etc/rc.d/S99stvor-restore`.
  Логика: cream и оба расширения на месте — выход; иначе `apk add bash curl ca-bundle` → tar.gz cream (сверка sha) →
  `cream system init` → `cream source add` (снимок, sha) → `cream install teleport-openwrt` (маркер есть — данные не
  трогает, `join` не вызывается) → `cream install stvor-agent-openwrt` → `/etc/init.d/teleport start`, службы агента.
  Повтор безопасен. cream не меняется (ADR 0005 п. 8 в силе).
- **Повтор команды портала** на роботе с маркером, данными и токеном `robot-<id>-*` — без `TELEPORT_FORCE`
  (идемпотентная ветка ядра): тот же узел.
- **«Новый секрет» на живой идентичности** — всегда новый `host_uuid` (Teleport 18.10). Портал предупреждает, если
  узел робота в сети; когда новое поколение привязалось (`bound_host_id`), Stvor удаляет `node/<старый bound_host_id>`.
- Пины на зеркале устарели — служба не восстановит; путь — «Новый секрет». Откат решения — убрать `keep.d/stvor`.
- Без маркера `/opt/teleport/.cream-owned` — по-прежнему отказ «Teleport не от cream». Debian не затронут.

## 5. Поток регистрации
```
портал → «Добавить робота» → строка OpenWrt:
  uclient-fetch -qO- --post-data='' --ca-certificate=/etc/ssl/certs/ca-certificates.crt …/install/<код> | sh
  sh: проверки (ID=openwrt ≥ 25.12, arch и набор в пинах, root, ОЗУ/место, нет Teleport не от cream)
     → apk add bash curl ca-bundle → cream tar.gz → cream system init → cream source add stvor (общий снимок)
     → cream install teleport-openwrt (набор openwrt-<arch>) → cream run teleport-openwrt join (секрет на stdin)
     → cream install stvor-agent-openwrt (tar.gz) → /etc/init.d/stvor-agent{,-telemetry} enable+start
     → /etc/stvor/restore.sh + /etc/init.d/stvor-restore + /lib/upgrade/keep.d/stvor
перезагрузка → procd: teleport (respawn, /opt/teleport/data), stvor-agent; S95cream-configure — configure по отметке
sysupgrade (с конфигурацией) → S99stvor-restore: apk, cream, расширения по пинам → teleport start без join
```

## 8. Риски
1. **`tsh ssh` через glibc на musl** (utmp, PTY, NSS в дочернем `teleport exec`) — единственный непроверенный кусок A.
   Смягчение — срез 0 первым; провал — стоп и B.
2. **Регресс `debian/teleport` при выносе ядра** — все Debian-роботы. Смягчение — без изменения поведения, тесты без
   правок ожиданий, живой прогон, `robots-gate` Debian до подъёма пина Stvor.
3. **Расхождение двух `teleport`** — смягчение: одно ядро в git, копии в снимке сверяет `check.sh`, `check-version-bump`
   поднимает всех потребителей.
4. **tmpfs `/var` и `sysupgrade`** — смягчение: раскладка `/opt/*`, `validate.openwrt_tmpfs`, тест с перезагрузкой,
   служба `stvor-restore` (Р4) и сценарий `sysupgrade` в приёмке. Архив `sysupgrade` с токенами — секрет уровня root
   (§9); устаревшие пины на зеркале — восстановление «Новым секретом».
5. **Пересечение с сессией Stvor** (телеметрия, общие файлы, общий стенд) — смягчение: свои функции в конце
   `robot_api.py`, свои строки `.env.example`, `x-runtime-env` и `RuntimeSettings`, в Traefik — только `rule` и
   отдельный middleware роутера `robot-install` (Р12), кто готов первым — сливает первым, второй ребейзит; пауза
   операций стенда по сигналу (правило плана).
6. **Одноразовый код и отказ скрипта** (Р5) — принято осознанно; проверки идут первыми.

## 9. Безопасность
- Секрет регистрации — по-прежнему на stdin `cream run teleport join`; на OpenWrt нет systemd-песочницы — процессы
  `teleport` и `stvor-agent` под root без ограничений (телеметрия — под своим пользователем); явно в `SECURITY.md`
  stvor-agent и README расширений.
- glibc-рантайм — из `.deb` Debian 12 по пинам sha256; CVE glibc — подъём пинов и пересборка набора (runbook Stvor 07).
- `keep.d` хранит ключи узла и токены stvor-agent в архиве `sysupgrade` (в ОЗУ на время обновления) — как
  `/etc/config` и `/etc/shadow`. Архив и его выгрузки (`sysupgrade -b`, LuCI) — секрет уровня root; восстанавливать
  только на ту же машину; при удалении робота — отзыв токенов агента и `tctl lock` на server-id (§4.3, Р4).
  Рецепт `stvor-restore` секретов не содержит.
- `POST` на install-эндпоинте: код — секрет в пути; CORS не открываем; погашение `POST`-ом пишется в аудит так же,
  как `GET` с заголовком.
- Временные пользователи стенда — только `owrt-*`, удаляются сразу после проверки вместе с токенами и узлами.

## 10. Отвергнутые варианты
| Вариант | Почему нет |
|---|---|
| Teleport в Docker на OpenWrt | SSH-сессии в ФС контейнера, `nsenter`, Docker на RPi тяжёл и лезет в fw4 |
| `gcompat` | нет в фидах, на aarch64 ненадёжен |
| `ld.so --library-path` без patchelf | `/proc/self/exe` указывает на загрузчик — ломает перезапуск себя для SSH-сессий |
| glibc в `/lib` | смешивает `libgcc_s` musl/glibc, ломает систему при обновлении пакетов |
| procd `stdout/stderr 1` у `teleport` | `LD_PRELOAD` musl в glibc-процессе — две libc (PoC); вместо — `log.output` в файл |
| `log.output: syslog` (`logread -e teleport`), даже с тегом `teleport[<pid экземпляра>]` | syslog принимает любой тег с любым pid от любого локального процесса — подделка отказа стирала бы секрет регистрации (ревью безопасности 2026-10-22) |
| Пакеты `.ipk`/`.apk` | два формата, apk v3 nfpm не пишет; tar.gz уже выпускается (В5) |
| Поддержка 24.10 (`opkg`) | «outdated», второй пакетный менеджер (В1) |
| Выбор ОС при создании робота | скрипт определяет сам (В2) |

## 12. Рулинги (контроллер)
| № | Риск / вопрос | Решение |
|---|---|---|
| Р1 | Строка `wget … \| sh` не шлёт `X-Stvor-Install` | сервер принимает `POST` как равноценный заголовку; строка OpenWrt — `uclient-fetch -qO- --post-data='' --ca-certificate=/etc/ssl/certs/ca-certificates.crt '<url>' \| sh` без `sudo`, без ca-bundle — отказ (§4.5) |
| Р2 | `/tmp`, `/var` — tmpfs | рабочие каталоги на диске (`/opt/…`, `TMPDIR`); набор без `tsh`; проверка места на `/opt` и `/tmp` (§3, §4.5) |
| Р3 | Как делить `teleport.sh` | одно ядро `lib/teleport-core.sh`, тонкие слои; контракт cream/v1 не меняется; **копии — по Р11** |
| Р4 (пересмотрен 2026-10-23, решение владельца) | Как робот переживает `sysupgrade` | **сам, тем же узлом.** `keep.d` расширений хранит идентичность Teleport (`/opt/teleport/data`, маркер, флаг `agent-enabled`), домены `/etc/cream/{teleport,stvor-agent}-openwrt`, токены и состояние агента; скрипт Stvor кладёт службу `stvor-restore` с рецептом без секретов (зеркало, пины). На первой загрузке служба ставит apk-зависимости, cream и оба расширения и запускает узел **без `join`** — тот же `host_uuid`, без портала. Реестр cream не сохраняется (cream не меняется, РО5, ADR 0005 п. 8). «Новый секрет» — только при потерянной идентичности; он всегда даёт новый `host_uuid` (Teleport 18.10), Stvor удаляет старый узел. Архив `sysupgrade` — секрет уровня root, восстанавливать только на ту же машину (§4.3, §4.7, §9) |
