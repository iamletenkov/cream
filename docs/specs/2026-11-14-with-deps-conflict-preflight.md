# Предпроверка файлов графа установки (#57)

До исполнения графа `install --with-deps` cream проверяет все назначения
`files[].dst`: между запрошенными расширениями, по реестру всех статусов
(даже без читаемого дерева) и через `Lstat` на машине. `src` — относительный
файл дерева, `dst` — уже проверенный чистый абсолютный путь; glob-развёртки нет.
Проверяется и пересечение «файл — родитель другого файла», и каталог вместо
собственного файла: такой upgrade также отказывает кодом 67 до исполнения графа.
Граф строится в `Engine.InstallAll`: `installWithDeps`, затем `resolve.Resolve`.
Resolver заменяет установленный узел новой версией того же имени; собственные
владения не конфликтуют. Предпроверка последовательно моделирует реестр по слоям:
если более раннее обновление владельца убирает путь из `files`, следующему слою
разрешена передача этого пути. До соответствующего слоя и для владельца вне
графа старое владение сохраняется. Реальная раскладка повторяет проверку после
фактического удаления старых файлов; не удаляемые при снятии ссылки и каталоги
не считаются освобождёнными файлами.
Для изменённого снимаемого файла также резервируется его будущее имя
`.cream-modified[.N]` с учётом существующих и уже запланированных файлов:
следующий слой не может затереть эту копию или столкнуться с ней после записи.
Владение точное: собственный прежний файл `/a` не даёт права переписать
неучтённый `/a/b`, даже если пользователь заменил `/a` каталогом.
Коды прежние: 67 `conflict.file`, `conflict.file_owner`, `conflict.file_unowned`;
диагностика содержит путь и имена владельцев, для чужого файла — отсутствие владельца.
`--accept-risk` разрешает только `targets.live: confirm`, а не конфликт файлов.
Висячая ссылка в родительских компонентах назначения даёт 74 `file.stat`
до исполнения любого слоя, в том числе в dry-run.

`install --dry-run` проходит ту же проверку и возвращает слои со статусом
`planned`, `changed: false`, без хуков и записей. Предварительная проверка
выполняется до создания lock-файла; обычная установка повторно читает источники
и реестр и проверяет граф под `lock/global`. Только затем возможны policy-rc.d,
стейджинг, домены, files, хуки и журнал. Проверка не предсказывает произвольные
изменения хуков: файлы, не объявленные в `files`, видны только если уже существуют.
Отказ первого прохода не создаёт даже блокировок. Если состояние изменилось
между проходами, возможны служебные lock-файлы; данные расширений не записываются.
Изменившийся источник даёт прежний 75 `lock.changed`: параметры, включая stdin,
разбираются один раз и не могут примениться к другой схеме.

## Отвергнутые варианты

- Откат уже поставленных зависимостей: не обеспечивает отсутствие изменений.
- Проверка только resolver: не видит существующих неучтённых файлов на диске.
- Снять старые владения сразу для всего будущего графа: файл может освобождаться
  более поздним слоем. Разрешается только освобождение более ранним обновлением
  в фактическом топологическом порядке; неизменяемый слой владение не снимает.
- Новый код выхода: существующего 67 достаточно.
